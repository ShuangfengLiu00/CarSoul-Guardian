## 一、数据来源说明

### 1.1 数据来源声明

CarSoul Guardian 在 Demo / 比赛阶段所展示的全部车辆数据，均来自**虚拟车模拟器**（`vehicle_protocol/simulator`），而非任何真实车辆。系统不存在与真实车辆 OBD 接口、CAN 总线、车企 OTA 平台的实时连接。

具体数据来源分三类：

| 类别 | 来源 | 说明 |
|------|------|------|
| 公开知识 | 公开车型资料、SAE/OBD-II 标准、公开论文、公开维修资料 | 故障码定义、电池热管理模型、知识库文档 |
| 模拟数据 | `vehicle_protocol/simulator` 虚拟车模拟器生成 | 驾驶行为、传感器读数（温度/电压/压力）、维修记录、衰减曲线 |
| 系统生成 | 数字孪生实时计算 | 健康评分、VSS 灵魂指数、生命周期事件 |

### 1.2 Q7 三要素：数据类型 / 来源 / 授权

参赛手册 Q7 要求披露数据的三要素（类型、来源、授权），逐项说明如下：

| 要素 | 披露内容 |
|------|----------|
| **数据类型** | ① 车辆静态属性（VIN、品牌、型号、电池容量、动力类型）；② 车辆动态遥测（电池温度、电机温度、胎压、SoH、SoC、电压、电流）；③ 驾驶行为数据（驾驶风格、日均里程、平均速度、快充比例、安全评分、能耗评分）；④ 维保记录（保养时间、里程、项目、费用）；⑤ 生命周期事件（诞生、里程碑、告警、故障、维修、退役）；⑥ 售后工单数据（服务类型、状态流转、费用、反馈）；⑦ Agent 推理过程数据（感知结果、诊断结论、专家会诊、风险预测、建议文本）。以上全部为**模拟生成或系统计算**，无任何真实车辆数据。 |
| **数据来源** | ① 公开知识：SAE J1979 OBD-II 标准、ISO 15118 充电协议、公开车型技术参数、公开电池衰减研究论文；② 模拟数据：`vehicle_protocol/simulator` 虚拟车模拟器（时间压缩引擎，确定性种子生成）；③ 系统生成：数字孪生引擎实时计算（健康评分算法、VSS 灵魂指数模型、风险预测模型）；④ 知识库：基于公开维修资料构建的故障模式库（`failure_patterns/*.yaml`）与维修案例库（`repair_cases/*.yaml`）。**不读取**任何真实车辆 OBD/CAN 接口、车企 TSP 平台、4S 店 DMS 系统。 |
| **授权说明** | ① 公开知识：来自公开标准与论文，无需授权；② 模拟数据：由系统自有的虚拟车模拟器生成，所有权归 CarSoul Guardian 项目，无第三方授权需求；③ 演示用户账户：使用模拟的用户名（如「demo_user」）与邮箱（如 `demo@carsoul.local`），不关联任何真实身份，无需用户授权；④ 数据出境：Demo 阶段全部数据在本地处理（SQLite），不上传任何第三方服务器，唯一可选的外部调用为 OpenAI API（仅发送车辆传感器模拟数据与诊断上下文，不发送个人隐私），且该调用为完全可选，无 Key 时自动降级。 |

### 1.3 模拟器定位

虚拟车模拟器是一个**时间压缩引擎**（Time-Compression Engine）。调用 `VirtualVehicle.run(days=365)` 可在数秒内合成一整年的每日遥测快照（`TelemetryFrame`）。每个快照是车辆在某一时刻的完整状态点，所有部件状态按照车型画像的衰减曲线与激活的场景演化。

模拟器的核心特性：
- **可复现**：相同的 `profile + seed + scenario` 组合始终产生完全一致的输出。
- **可追溯**：每个 `TelemetryFrame` 的字段均可追溯到具体的衰减公式与场景参数。
- **无真实数据**：不读取任何真实车辆接口，不涉及任何真实车主信息。

## 二、模拟逻辑说明

### 2.1 三个车型画像

模拟器内置三个车型画像（`VehicleProfile`），分别代表三种典型的新能源用车场景：

| 画像 | 品牌/型号 | 动力类型 | 电池容量 | 用车场景 |
|------|-----------|----------|----------|----------|
| `performance_ev` | Tesla Model S Plaid | 纯电动 | 100 kWh | 高性能 EV |
| `family_ev` | BYD Han EV | 纯电动 | 60 kWh | 家庭 EV |
| `hybrid` | Toyota Prius | 插电混动 | 18 kWh | 日常通勤 |

### 2.2 衰减曲线（Degradation Curves）

每个画像定义了每 10,000 公里的部件衰减速率，模拟器根据行驶里程、驾驶风格与充电习惯进行调制。基础衰减参数如下：

| 衰减参数 | `performance_ev` | `family_ev` | `hybrid` | 说明 |
|----------|:-:|:-:|:-:|------|
| 电池 SoH 损失 (%/万km) | 1.0 | 0.6 | 0.5 | 高功率车型衰减更快 |
| 电机磨损 (/万km) | 0.035 | 0.025 | 0.030 | 0-1 标准化磨损 |
| 刹车片磨损 (/万km) | 0.08 | 0.10 | 0.12 | EV 再生制动减少刹车片磨损 |
| 轮胎磨损 (/万km) | 0.12 | 0.075 | 0.08 | 高扭矩导致轮胎磨损加快 |
| 悬挂健康损失 (/万km) | 2.5 | 1.5 | 2.0 | 0-100 分值下降 |
| 快充应力倍率 | 1.6 | 1.4 | 1.3 | 快充比例 > 50% 时额外加速 SoH 衰减 |
| 激进驾驶倍率 | 1.6 | 1.5 | 1.4 | 激进驾驶风格放大全部磨损率 |

**调制逻辑**：
- 驾驶风格倍率（`style_multiplier`）：eco = 0.7，balanced = 1.0，sporty = 1.2，aggressive = 画像的 `aggressive_multiplier`。
- 快充应力：当 `fast_charge_ratio > 0.5` 时，SoH 损失额外乘以 `fast_charge_stress × (ratio - 0.5) / 0.5`。
- 异常注入：场景可注入冷却故障、电芯失衡等异常，使衰减加速至最高 3 倍。

### 2.3 传感器基准（Sensor Baselines）

每个画像定义了传感器的标称工作点，模拟器在其周围施加高斯抖动并随部件衰减进行漂移：

| 传感器基准 | 默认值 | `performance_ev` | `family_ev` | `hybrid` |
|------------|--------|:-:|:-:|:-:|
| 电池温度 (°C) | 28.0 | 30.0 | 27.0 | 26.0 |
| 电机温度 (°C) | 45.0 | 50.0 | 43.0 | 48.0 |
| 胎压 (bar) | 2.4 | 2.4 | 2.4 | 2.4 |
| 座舱温度 (°C) | 23.0 | 23.0 | 23.0 | 23.0 |
| 电池温度抖动 σ (°C) | 3.0 | 4.0 | 3.0 | 3.0 |
| 电机温度抖动 σ (°C) | 5.0 | 5.0 | 5.0 | 5.0 |
| 胎压抖动 σ (bar) | 0.08 | 0.08 | 0.08 | 0.08 |

**告警阈值**（模拟器在异常场景下将传感器值推向这些阈值）：

| 阈值 | 默认值 |
|------|--------|
| 电池温度警告 (°C) | 45.0 |
| 电池温度危险 (°C) | 55.0 |
| 电机温度警告 (°C) | 90.0 |

### 2.4 行为模型（Behaviour Model）

每个画像定义了驾驶风格的概率分布与评分基准：

| 行为参数 | `performance_ev` | `family_ev` | `hybrid` |
|----------|:-:|:-:|:-:|
| eco 风格占比 | 15% | 35% | 40% |
| balanced 风格占比 | 45% | 50% | 45% |
| aggressive 风格占比 | 25% | 8% | 8% |
| sporty 风格占比 | 15% | 7% | 7% |
| 安全评分基准 | 82.0 | 88.0 | 87.0 |
| 能耗评分基准 | 75.0 | 85.0 | 88.0 |
| 日均里程范围 (km) | 5–200 | 3–100 | 3–90 |
| 日均里程均值 (km) | 55 | 35 | 38 |
| 平均速度范围 (km/h) | 30–80 | 20–65 | 22–68 |
| 默认快充比例 | 0.50 | 0.25 | 0.15 |

**评分计算逻辑**：
- 安全评分 = 基准 + 风格调整（eco +8 / balanced 0 / sporty −8 / aggressive −18）− 刹车磨损 × 10 − 轮胎磨损 × 8 + 高斯噪声。
- 能耗评分 = 基准 + 风格调整 − max(0, 快充比例 − 0.4) × 15 + 高斯噪声。

### 2.5 场景编排（Scenario Orchestration）

模拟器通过场景配置控制数据演变的故事线，支持以下场景元素：

| 场景类型 | 说明 |
|----------|------|
| `ChargingHabit` | 控制快充比例随时间的变化（基础比例 + 年漂移） |
| `SeasonalTemp` | 按月份调制环境温度与电池温度（温带气候月度基线） |
| `RoadMix` | 道路类型权重（城市/高速/郊区/山区/乡村） |
| `AnomalyInjection` | 在特定时间点注入部件故障（冷却故障/刹车故障/电芯失衡/电机过热） |

内置预设场景：
- `normal_lifecycle()`：正常生命周期，适度充电，无异常。
- `aggressive_lifecycle()`：激进生命周期，高快充比例，快速磨损。
- `cooling_fault_scenario()`：冷却系统故障场景（第 2 年发展），用于演示 Agent 异常感知与诊断闭环。

### 2.6 时间线 Demo 确定性保证

后端时间线服务（`timeline_service.py`）作为「一辆车的生命故事」叙事生成器，严格遵守以下确定性约束：

| 约束 | 实现 |
|------|------|
| **demo_mode 始终为 True** | `LifeStoryResponse.demo_mode` 硬编码为 `True`，响应体中始终携带该字段 |
| **确定性输出** | 全部数据为硬编码的确定性数据结构（非随机生成），相同请求始终返回完全一致的响应 |
| **无外部依赖** | 自包含 Demo 数据生成器，不依赖模拟器内核或外部服务 |
| **VIN 模拟标识** | 使用 `VFSIM-2025-00042` 前缀，明确标识为模拟数据 |
| **前端角标** | 时间线 Demo 页面（`TimelineDemo.tsx`）渲染红色「演示模式 · 模拟数据」角标 |

## 三、脱敏说明

### 3.1 VIN 模拟生成

系统中出现的所有 VIN（车辆识别号）均为**模拟生成**，不对应任何真实车辆：

| VIN 前缀 | 生成位置 | 生成规则 | 示例 |
|----------|----------|----------|------|
| `VFSIM-` | 后端时间线服务（`timeline_service.py`） | `VFSIM-{年份}-{序号}` | `VFSIM-2025-00042` |
| `VSIM` | 虚拟车模拟器（`virtual_vehicle.py`） | `VSIM{seed:06d}00000`（由随机种子确定性生成） | `VSIM00004200000` |

两个前缀均以 `SIM`（Simulated）标记，明确标识为模拟数据。任何 `VFSIM-` 或 `VSIM` 开头的 VIN 均可一眼识别为非真实车辆。

### 3.2 无真实个人信息

- 系统的数据模型围绕**车辆实体**设计，不包含独立的个人隐私字段（无真实姓名、身份证号、手机号、位置轨迹）。
- 权限模型（`governance/permissions.py`）中设有**永久禁止列表**（`FORBIDDEN`），任何 Agent 均无法访问以下资源：
  - `read_user_location`（用户位置）
  - `read_payment_data`（支付数据）
  - `read_personal_info`（个人信息）
- 演示用户账户使用模拟的用户名与邮箱，不关联真实身份。

### 3.3 售后工单数据脱敏

售后闭环功能（§3A.1）涉及的工单数据同样遵循脱敏原则：

| 字段类别 | 脱敏措施 |
|----------|----------|
| 服务提供商名称 | 使用模拟名称（如「星辰服务中心」），非真实 4S 店/维修厂 |
| 工单费用 | 模拟金额，基于公开保养价格区间生成，非真实交易数据 |
| 用户反馈文本 | 演示用预设反馈，非真实用户输入 |
| 诊断关联 | 引用 Agent 推理过程（模拟数据），不关联真实诊断报告 |

## 四、不替代专业判断声明

CarSoul Guardian 提供的诊断建议、风险预测、健康评分均为**辅助参考信息**，不构成专业维修建议。

### 4.1 明确声明

1. **辅助定位**：系统定位为「辅助分析 / 预测 / 建议 / 提醒」，像免疫系统而非大脑。系统**不替代**专业维修技师的检测与判断。
2. **准确性边界**：系统通过传感器模拟数据与 AI 模型进行分析，但不保证分析结果的绝对准确性。风险预测准确率基于模拟数据统计，不代表对未来事件的确定性判断。
3. **专业检修优先**：所有告警的 `recommendation` 字段始终包含专业检修建议。严重故障建议直接联系服务中心。车辆故障诊断与维修请以专业检修机构结论为准。
4. **责任限制**：在适用法律允许的最大范围内，系统不对因依赖 AI 建议而导致的任何直接、间接、附带或后果性损失承担责任。

### 4.2 工程落实

- 前端「安全合规」页面（`SafetyCompliance.tsx`）内置完整免责声明弹窗，涵盖服务性质、准确性声明、驾驶安全、数据使用、责任限制五个方面。
- 前端所有页面设计为**停车状态下通过车机大屏交互**，驾驶过程中严禁操作系统。

## 五、守护非控制原则

### 5.1 核心原则

CarSoul Guardian 坚守「**守护非控制**」（Guard-Not-Control）红线：Agent 仅给出建议与提醒，**不替用户执行任何不可逆操作**，更不控制车辆任何执行机构。

### 5.2 工具层无控制能力

AI Agent 工具注册表中**不存在任何控制执行器的工具**。具体而言：

- **无** `brake`（刹车控制）
- **无** `steer`（转向控制）
- **无** `accelerate`（加速控制）
- **无** 任何向车辆发送控制指令的工具

工具层仅提供以下两类工具：

| 类别 | 工具 | 能力边界 |
|------|------|----------|
| 读工具（6 个） | `get_vehicle_info`、`get_health_score`、`get_maintenance_plan`、`get_driving_behavior`、`get_lifecycle_timeline`、`get_alerts` | 仅查询，只读 |
| 守护工具（4 个） | `push_reminder`、`record_lifecycle_event`、`write_service_suggestion`、`create_service_order` | 仅提醒/记录/写入建议文本/创建外部工单，不控制车辆 |

> **结构性闸门**：即使 LLM 产生幻觉试图调用 `/control/*`，工具注册表中也没有对应条目可以分发——边界通过结构而非提示词礼仪来保证。所有守护动作记录在 `ActionStore` 中（持久化至 SQLite），可供审计。

### 5.3 治理层默认只读

权限模型（`governance/permissions.py`）采用**最小权限原则**（Least Privilege）：

- 权限链路：`Agent → Role → Permission → Data`
- 每个子 Agent 与专家角色仅声明其领域所需的数据访问权限。例如电池专家只能读取电池数据，底盘专家只能读取刹车与轮胎数据。
- **写入权限严格受限**：全部权限中仅 `WRITE_DIGITAL_TWIN`（写入数字孪生）与 `SEND_REMINDER`（发送提醒）两个写入权限存在，且仅授予 `orchestrator` 与 `service_suggestion` 角色。
- **禁止列表永久生效**：`read_user_location`、`read_payment_data`、`read_personal_info` 三个权限被列入 `FORBIDDEN` 集合，`PermissionChecker` 对任何 Agent 的此类请求一律拒绝并记录警告日志。
- 主动巡检调度器（APScheduler）仅在后台执行**只读分析**（查询数据、生成预测），不执行任何写入或控制操作。

## 六、演示模式标识

### 6.1 标识规范

依据 `docs/schema-spec.md` 的模拟数据声明：**所有演示页面须标注红色「演示模式 · 模拟数据」角标**。

### 6.2 DemoBadge 统一标注体系

为实现标识的统一性与一致性，系统采用**集中式 `DemoBadge` 组件**（`frontend/src/components/DemoBadge.tsx`）作为所有模拟数据页面的唯一标注入口：

| 特性 | 说明 |
|------|------|
| **统一文本** | 所有页面显示一致的红色角标文本：「演示模式 · 模拟数据」 |
| **Tooltip 说明** | 鼠标悬停显示：「本页面使用模拟数据，仅用于功能演示，不代表真实车辆状态。后端 demo_mode=true，返回确定性结果。」 |
| **位置模式** | 支持 `top-right`（默认）、`top-left`、`bottom-right`、`bottom-left` 四种固定位置 + `inline` 行内模式 |
| **覆盖范围** | 已集成至全部 17 个 Demo 页面：时间线 Demo、故事模式、车辆模拟器、10 个全息页面、车辆档案（含售后工单 Tab）、仪表盘、风险预测、Agent 对话 |
| **红线对齐** | 对应 GOAI 红线 2（消除「虚假演示」隐患）：所有模拟数据页面均有醒目标识，评审与用户不会误认为真实车辆数据 |

### 6.3 标识落实清单

- 所有 Demo 页面通过 `<DemoBadge />` 组件统一渲染红色角标。
- 故事模式页面（`/story` 路由）的模拟数据由 `frontend/src/services/storyData.ts` 提供，自包含运行无需后端。
- 时间线 Demo 后端 `demo_mode` 始终为 `True`，返回确定性结果，重复调用输出完全一致。
- 系统在数据来源层面透明披露：PPT 与文档中明确区分「公开知识」「模拟数据」「系统生成」三类数据来源。
- GOAI 赛题明确允许模拟数据与模拟业务。Demo 的重点是验证 Agent 的感知、推理、调用能力与闭环完整性，而非数据是否来自真实车辆。

## 七、售后闭环合规（§3A.1）

### 7.1 功能概述

售后闭环功能实现了从 Agent 诊断 → 工单创建 → 进度追踪 → 完成反馈的完整闭环，状态机如下：

```
created → booked → in_service → done → closed
```

### 7.2 合规要点

| 合规维度 | 措施 |
|----------|------|
| **数据持久化** | 工单数据持久化至主数据库（SQLite/PostgreSQL），非内存临时存储，可供审计追溯 |
| **状态流转单向** | 状态机为前向流转（`STATUS_FLOW`），不可逆向回退，确保工单生命周期不可篡改 |
| **状态历史** | `status_history` 字段（JSON 数组）记录每次状态变更的时间戳与备注，完整审计链 |
| **用户反馈闭环** | 工单到达 `done` 或 `closed` 时收集用户反馈（`confirmed` / `false_alarm` / `no_event` / `partial`），实现人机协同决策 |
| **诊断可追溯** | `diagnosis_summary` 字段关联触发该工单的 Agent 诊断结论，形成「诊断 → 工单 → 反馈」完整证据链 |
| **级联删除** | 工单通过 `vehicle_id` 外键关联车辆，`ondelete="CASCADE"` 确保车辆删除时工单一并删除，保障数据删除权 |
| **无真实交易** | 工单费用为模拟金额，服务提供商为模拟名称，不涉及真实支付或真实服务商 |

## 八、行业边界声明

### 8.1 系统能力边界

CarSoul Guardian 定位为**车辆生命周期守护智能体**，其能力边界明确如下：

| 能力 | 说明 |
|------|------|
| **能做** | 车辆健康监测与评分、故障模式识别与根因推理、维修保养建议与提醒、驾驶行为分析与改善建议、二手车残值评估参考、售后工单全生命周期追踪 |
| **不能做** | 不控制车辆任何执行机构（刹车/转向/加速）、不替代专业维修技师的检测与判断、不提供法律或保险建议、不进行实时导航或路径规划、不直接对接车企 OTA 或 TSP 平台 |

### 8.3 数据落地路线（未来规划）

当前 Demo 阶段全部使用模拟数据。未来真实数据接入的三线并行路线：

| 路线 | 方案 | 阶段 |
|------|------|------|
| 主线 | 车企 TSP/OTA 平台数据接口对接（需车企授权） | 产业化阶段 |
| 备线 | 后装 OBD-II 蓝牙设备采集（通用协议，无需车企授权） | PoC 验证阶段 |
| 对冲 | 保险/4S 渠道合作获取维保记录（需合作伙伴授权） | 商务拓展阶段 |

> **合规承诺**：任何真实数据接入均将遵循「用户明示授权 + 最小必要采集 + 本地化处理 + 可随时删除」四原则，并在接入前更新本合规文档。
