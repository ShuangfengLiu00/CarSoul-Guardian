# CarSoul Guardian UI/UX 开发规范 V1.0

> 生效范围：`frontend/` 全部页面与组件（含 hologram 演示层）
> 制定依据：产品定位（AI 车辆医生 · 三条红线）+ GOAI 参赛手册 8.3 产品体验要求 + 2026-08-04 UI 审查结论
> 执行方式：本规范是 PR 自查与封版验收的强制清单，第 11 章 Definition of Done 逐条过

---

## 1. 设计原则（不可违反）

### P1 医生在场原则
每个车主可见页面必须包含一处"医生视角"的自然语言结论，不允许只陈列数据。
- ✅ "你的车健康 87 分。刹车片磨损接近阈值，建议 2 周内检查。"
- ❌ 只放 5 张图表一张表，让用户自己解读。

### P2 闭环可见原则
凡是 Agent 给出的建议，UI 必须提供"行动入口"与"后续状态"，闭环四段缺一不可：
**分析 → 建议 → 行动（采纳/预约/提醒）→ 追踪（状态流转可见）**。
只读的 Trace 展示不算闭环。

### P3 守护非控制原则
UI 上禁止出现任何"替用户执行不可逆操作"的交互（如"远程熄火""自动维修下单"）。
所有行动按钮的语义是"提醒/记录/建议"，落地到 guard_tools 三件套。

### P4 真实标注原则
使用模拟数据的页面必须挂 `<DemoBadge />`（组件已存在，`components/DemoBadge.tsx`）。
演示内容与真实能力必须可被评委一眼区分——这是 GOAI 红线，不是美观问题。

### P5 分层可见原则
界面按用户分层展示：车主层（默认）→ 进阶层 → 演示层（评委模式开关）。
技术实现细节（Token、向量后端、Registry）永不出现在车主层。

## 2. 信息架构规范

### 2.1 三层分组（菜单唯一合法结构）

| 层级 | 可见性 | 页面 | 面向 |
|------|--------|------|------|
| ① 车主层 | 默认 | 今日诊断首页 / AI 守护对话 / 车辆档案 / 风险预测 | 车主 |
| ② 进阶层 | 默认，分组折叠 | 数字生命 / 灵魂主页 / 仿真检修 / 售后工单 | 深度车主 |
| ③ 演示层 | "评委演示模式"开关后显示 | 故事模式 / 全息座舱 / 治理控制台 / 进化引擎 / 安全合规 / 知识库 / 一辆车的一生 | 评委、开发者 |

### 2.2 导航规则
- 菜单项必须在 `App.tsx` 存在对应路由，加菜单前先加路由（当前 `/evolution` 为死链，属缺陷）。
- 有路由的车主/进阶层页面必须有菜单入口（当前 `/knowledge` 无入口，属缺陷）。
- 新增页面必须在 PR 描述中声明所属层级，未声明默认进演示层。
- 桌面侧栏分组标题：车主守护 / 深入了解 / 演示模式（开关控制）。
- 页面总数只减不增：功能重复页面（3 首页、2 对话、3 时间线）按收口计划合并，不再新建同类页面。

## 3. 文案与语气规范

### 3.1 人格
统一"主治医生"口吻：专业、笃定、有同理心、说人话。第一人称用"我"（指守护引擎），称用户的车为"你的车"。

### 3.2 禁用词表（车主可见层）

| 禁用 | 原因 | 替换 |
|------|------|------|
| TASK008/TASK009 等任务编号 | 暴露开发看板 | 删除或改功能名 |
| Registry / Sandbox / MCP / Token 消耗 | 工程术语 | 移至演示层 |
| 接口预留 / 将在 X 接入 | 半成品占位 | 功能不上线则不显示 |
| 向量后端 / 嵌入模型 | 技术细节 | "汽车知识库" |
| VSS 灵魂指数 | 玄学难懂 | "车辆活力指数" + 一行白话解释 |
| 生成365天生命周期 | 脚本口吻 | "回看这一年的用车故事" |
| 治理控制台 | 冷 | 演示层可保留，车主层禁止 |

### 3.3 推荐句式
- 结论先行："刹车片该换了" 优于 "根据数据分析，刹车片磨损率已达到……"
- 给时间窗："建议 2 周内处理"，不说"尽快"。
- 给确定性分级："基本确定 / 可能 / 需要进一步检查"三档，对应后端的 confidence。
- 风险话术必须带"建议到店由技师确认"——守护非控制的文案落地。

### 3.4 数字与格式
- 健康分数：整数 + /100；里程：万 km（≥1万）或 km（<1万）；费用：¥ + 千分位。
- 时间：今天/昨天/N 天前；超过 30 天显示具体日期。
- 空态必须有引导语 + 行动按钮，不允许裸 Empty。

## 4. 视觉系统规范

### 4.1 两套体系的定位

| 体系 | 定位 | 使用范围 |
|------|------|----------|
| 主线 AntD 浅色体系 | **产品本体** | 车主层 + 进阶层全部页面 |
| 全息深空体系（--holo-*） | **演示皮肤** | 仅演示层 /holo 路由下；必须在入口标注"概念演示"；禁止与主线互链 |

新功能永远先落在主线体系。全息体系只准维护，不准扩张。

### 4.2 主线设计 Tokens（已存在，直接引用）

| 用途 | Token / 值 | 规则 |
|------|-----------|------|
| 页面背景 | `--cs-bg: #f5f7fb` | 不许另设背景色 |
| 正文 | `--cs-text: #1f2937` | 次级文字用 AntD `Text type="secondary"` |
| 品牌主色 | `brand.500 #3b82f6` | 主按钮、链接、选中态 |
| 品牌渐变 | `135deg, #3b82f6 → #10b981` | **仅用于 AI 身份标识**（头像、Logo、守护状态），不得用于普通按钮背景 |
| 健康/正常 | `guardian.green #10b981` | 语义色，见 4.3 |
| 注意/提醒 | `guardian.amber #f59e0b` | 语义色 |
| 严重/危险 | `guardian.red #ef4444` | 语义色 |
| 字体 | Inter + PingFang SC + Microsoft YaHei | 已配置，勿改栈 |

### 4.3 语义色铁律（医疗隐喻）
颜色即诊断语言，全站一致：
- 绿 = 健康/正常/已解决；琥珀 = 需关注/临近阈值；红 = 严重/立即处理。
- 禁止用红表达"选中""热门"等非危险语义；禁止用绿表达"进行中"。
- 健康分数段：≥85 绿 / 70–84 琥珀 / <70 红（与后端 health level 对齐）。

### 4.4 图表规范（Recharts）
- 每个图表必须有"一句话读法"（标题下方 12px 灰字），回答"这张图告诉车主什么"。
- 雷达图 ≤6 维；趋势图必须标出当前值与阈值线。
- 图表不是结论——图表上方或右侧必须有 P1 原则要求的自然语言结论。

### 4.5 布局与组件风格
- 卡片：AntD Card + `cs-card` 类，圆角 12-14px，轻边框（1px #eef0f4），不用重阴影。
- 按钮主操作圆角 10-12px，高度 ≥44px（移动端触控）。
- 间距体系：8 的倍数；页面主体最大宽度沿用 `cs-content-wrap`。

## 5. 核心交互组件规范

### 5.1 ClosedLoopTrace（已有）
- 用途：展示 Agent 单次响应的"感知→诊断→风险→建议→执行"轨迹。
- 聊天流内用 `compact`；详情页用完整版。
- 仅展示，不承担行动（行动走 5.3）。

### 5.2 会诊面板 ExpertPanel（新建，P0）
- 场景：AgentChat 的 thinking 阶段及诊断类回答下方。
- 数据源：后端响应已有的 `expert_opinions`（10 专家），实时渲染各专家结论（专家名/专科/finding/severity/confidence）。
- 视觉：专家卡片横排或折叠列表，severity 用 4.3 语义色；最后汇总卡 = "主治医生结论"。
- 这是"多智能体会诊"在真实产品里的唯一窗口，StoryMode 的会诊叙事以此为准（材料一致性红线）。

### 5.3 建议行动卡 SuggestionCard（新建，P0）
- 每条建议必须带行动按钮组：`预约保养` / `设为提醒` / `已处理`。
- 按钮落地：调用 guard_tools（push_reminder / record_lifecycle_event / write_service_suggestion），成功后状态可见（Tag：已提醒/已记录/已处理）。
- 处理结果回流风险预测反馈接口（/api/risk/.../feedback），形成真实闭环数据。

### 5.4 CriticalAlertOverlay（已有）
- 仅 severity=critical 触发，每会话同告警不重复霸屏。
- 必须带"查看详情"与"我知道了"，禁止"一键消除告警"语义。

### 5.5 DemoBadge（已有）
- 所有 mock 驱动页面强制挂载；演示层页面默认 `inline` 放在标题旁。
- 故事模式、全息座舱、仿真检修（合成数据时）为必挂页面。

### 5.6 TripReportCard（已有）
- 仅在 closed_loop.trip_report 存在时渲染，置于气泡下方。

## 6. 页面模板规范

### 6.1 首屏三段式（车主层页面必须满足）
1. **今日诊断卡**：自然语言结论 + 最重要的 1-2 个建议 + 行动入口（P1+P2）。
2. **关键指标区**：≤4 个核心指标卡，语义色标注。
3. **详细数据区**：图表/表格，允许后置与折叠。

### 6.2 四态必备
每个数据页面必须实现：加载（Skeleton，禁止裸 Spin 居中）、空态（引导语+按钮）、异常（可重试，提示人话）、降级（后端不可用时明示"当前展示示例数据"并挂 DemoBadge）。

### 6.3 半成品禁令
任何页面不得出现"待接入/预留/TASKxxx"字样。功能未就绪 = 路由不上线。演示层除外，但需 DemoBadge。

## 7. 数据与 Mock 规范

- mock 统一收口到 `services/demoFixtures.ts`（单一来源），禁止页面级散落 mock（现状 demoData/holoData/storyData 三套并存，须合并）。
- 真实 API 失败时的兜底数据必须带 `__demo: true` 标记，UI 层据此挂 DemoBadge。
- 演示视频/PPT 中的界面截图必须来自挂有 DemoBadge 的页面或真实链路，二选一并在材料中注明。

---

## 8. 响应式与移动端

- 断点：沿用 `(pointer: coarse), (max-width: 1024px)` 判定平板/手机。
- 移动端底部 TabBar **最多 5 项**，只放车主层页面；其余页面收进"我的"或二级页。
- 触控目标 ≥44px；语音按钮保持 56px 现状。
- 移动端不做全息体系入口。

---

## 9. 可访问性

- 语义色必须搭配图标或文字（色盲友好），禁止颜色单通道编码。
- 霸屏告警可被键盘 Esc 关闭，焦点返回触发源。
- 语音输入状态必须有视觉指示（现状"● 正在聆听"保留）。
- 图表提供 aria-label 或下方文字结论（结论卡天然满足）。

## 11. Definition of Done（PR 自查清单）

每个前端 PR 合并前逐条确认：

- [ ] 页面有一处医生口吻的自然语言结论（P1）
- [ ] 建议类 UI 有行动按钮且落到 guard_tools（P2）
- [ ] 无控制类交互语义（P3）
- [ ] mock 页面挂 DemoBadge（P4）
- [ ] 页面层级已声明，菜单与路由一一对应（2.2）
- [ ] 无禁用词、无 TASK 编号、无占位文案（3.2 / 6.3）
- [ ] 语义色使用符合 4.3，未新增体系外颜色（4.2）
- [ ] 四态齐备：加载/空/异常/降级（6.2）
- [ ] 移动端 Tab ≤5，触控目标 ≥44px（8）
- [ ] 文案给时间窗、给确定性分级（3.3）
- [ ] 数字格式符合 3.4
- [ ] 演示层页面未与主线互链（4.1）
